# Annotation codebook v1.3

The rules for annotating an instrument. Vocabularies: `schemas/vocab.json`. Schema:
`schemas/annotation.schema.json`, generated by `tools/make_schema.py`. Validator: `tools/validate.py`.
Worked examples: `annotations/us-tx-tax-151.359.json`, `annotations/uk-osa-category-thresholds-2025.json`,
`annotations/it-garante-2023-chatgpt-limitation.json`, plus the Oct 2026 gold set (every file whose
`annotator.method` is "gold set (Opus, Claude Code)").

## 1. Principles

1. **Describe the text; don't interpret it.** Record what the instrument says, not its effects, its
   enforcement in practice, or research judgements such as whether it creates exogenous variation.
2. **Evidence for every fact.** Each event, threshold, obligation, sanction, definition, relation and entity
   carries `evidence: {provision, quote}`. The quote is verbatim from the annotated text (original language;
   an English gloss may follow in brackets). `tools/quote_check.py` must pass.
3. **Two kinds of field:**
   - **Facts:** events, thresholds, obligations, enforcement, definitions, relations, entities. They are
     verifiable by quote.
   - **Judgements:** summary and classification. They cannot be verified by quote. They are validated by
     agreement between independent annotations and by human spot-checks, and are always treated as machine
     output unless validated.
4. **Build from official texts only.** Never derive annotations from AGORA's or any tracker's summaries or tags
   (licences, and independence). AGORA's taxonomy *labels* are reused for compatibility; its data is not.
5. **Empty is never ambiguous.** A section with no entries must appear in `section_status` as
   `not_applicable` (the instrument by nature contains no such provisions; say where they live, if known) or
   `not_found` (it could, but the annotator found none).

## 2. Unit and version

- **One annotation file per instrument** (`annotations/<instrument_id>.json`). A part-of record (an NDAA
  section, a chapter) is annotated as its parent instrument, with `text_version.extent: "partial"` and the
  provisions covered listed in `text_version.note`.
- **"As of" a text.** `text_version` records the source, URL, retrieval date, version and extent:
  - `version` is consolidated as of a date, the original as adopted, made, or a bill text version;
  - `extent` is `full`, `partial` (selected provisions) or `excerpt` (one section of a code).
  Prefer consolidated texts. If only the original is available, say so, and record known later amendments
  only if the text itself mentions them.
- **Provision IDs.** Cite the smallest unit, in the text's own numbering, English labels for structure:
  `Art. 5(2)(b)`, `§ 11 Abs. 1 Nr. 2`, `Sec. 151.359(d)(2)`, `Annex III, point 5(b)`; Chinese `Art. 7 para. 2
  item (3)` (第七条第二款第（三）项). Text an amending act inserts into another act: `Art. 2 (inserting Lei
  11.196/2005, Art. 11-B §1 I)`. A Federal Register rule is annotated from its regulatory text (`extent: full`
  when the whole part is covered); the preamble is context, noted in `text_version.note`.
- **Amending acts that restate the amended law in full** (US session laws, many LATAM laws): annotate only the
  text the act adds or changes (underlined, bracketed or otherwise marked); restated unchanged text informs the
  summary and `relations` but is not coded as new events, thresholds or obligations. Say so in
  `text_version.note`. Notice duties toward employees or other affected persons use `notice_to_users`.
- **Proposals** (bills, draft regulations, NPRMs, EU Commission proposals, consultation drafts) are first-class:
  - Annotate the **latest text version**, naming it in `text_version.version` (e.g., "Senate-passed text,
    2024-12-10"; "Commission proposal COM(2025) 837").
  - When a new version passes a stage, write a new annotation. The previous file moves to
    `annotations/versions/<instrument_id>__<version-slug>.json`, so versions can be compared.
  - Obligations and thresholds in a proposal describe what *would* apply. `applies_from` keeps the proposal's
    own wording, e.g., "12 months after entry into force".
  - The instrument record carries `legislative_stage` and the proposal fields (`schemas/instrument.schema.json`).

## 3. Sections and fields

Required sections by tier (the validator enforces this):

| Section | A | B | C |
|---|---|---|---|
| summary, classification, events | ✓ | ✓ | ✓ |
| thresholds, relations | ✓ | ✓ | |
| obligations, enforcement, definitions, entities | ✓ | | |

### 3.1 Summary (judgement)

- `short`: at most 50 words. What the instrument does, to whom, and from when. No evaluation.
- `long`: at most 200 words. Adds the main mechanisms, thresholds, exceptions and enforcement. Neutral and
  factual; no adjectives such as "landmark" or "strict".

### 3.2 Classification (judgement)

| Field | Rule |
|---|---|
| `domains` / `primary_domain` | Subject matter. Use every domain that has operative provisions in the instrument, not ones merely mentioned, and not incidental riders (e.g., a clause sending fines to a children's fund). Primary = the domain most operative provisions serve |
| `mechanisms` | How the instrument acts (policy instrument type). See definitions below |
| `binding_force` | `binding` (statute, regulation, decree, order, ordinance); `quasi_binding` (codes or guidelines with legal effect, comply-or-explain, presumption of conformity); `non_binding` (strategies, recommendations) |
| `addressee_roles` | Who bears obligations or receives benefits under the text |
| `affected_roles` | Who is materially affected without being an addressee (e.g., users of a blocked service) |
| `decision_margins` | Which decisions of firms or households the operative provisions plausibly change. Code only margins tied to a specific provision |
| `territorial_scope` | `types` (one or more), a one-sentence description, and evidence. `extraterritorial` means it reaches actors outside the jurisdiction (e.g., by targeting its users); `targeted` means it is addressed to named entities |
| `agora_*` | AGORA taxonomy labels, used verbatim, only when clearly applicable. For instruments that are not AI-specific (e.g., a data-center tax exemption), the AI-specific lists (applications, risk factors) usually stay empty |

**Mechanisms.**
- `mandate_obligation`: positive duties.
- `prohibition_ban`: forbids conduct or products.
- `licensing_permit_certification`: prior approval required.
- `registration_notification`: register or notify, without approval.
- `designation_tiering`: sorts entities into categories with different rules.
- `disclosure_transparency`: information duties to the public or users.
- `tax_incentive`: exemption, credit or reduced rate.
- `direct_subsidy_grant`: payments or in-kind support.
- `tariff_price_regulation`: sets or approves prices or tariffs (e.g., large-load electricity tariffs).
- `moratorium_pause`: temporary freeze.
- `export_import_control`: licensing or bans on cross-border transfers of goods or technology.
- `investment_review`: screening of investments.
- `procurement_rule`: terms for government purchasing.
- `liability_rule`: civil liability allocation.
- `enforcement_order`: an individual measure against a named party.
- `institution_setup`: creates or empowers a body.
- `standard_setting`: technical standards.
- `sandbox_pilot`: experimental regimes.

**Domains** are listed in `vocab.json`. Notes on the less obvious ones:
- `generative_ai`: services that generate content.
- `synthetic_media_deepfakes`: rules on generated likenesses and labelling of synthetic content.
- `algorithmic_decision_systems`: automated decisions about people.
- `compute_data_centers`: data-center siting, incentives and operation.
- `energy_grid_water`: energy, grid and water rules affecting compute.
- `ip_training_data`: copyright, text-and-data-mining exceptions and training-data rights.

**Decision margins.** Firms:
- `entry_market_access`: whether a firm can enter or serve a market.
- `investment_location`: where and how much firms invest.
- `input_use`: use or price of compute, data, energy, chips or labour.
- `product_design_release`: features, model release, safeguards.
- `pricing`: prices firms charge.
- `trade`: cross-border sales and sourcing.
- `compliance_process`: internal processes, assessments, reporting.
- `size_organization`: firm size, structure, number of entities.

Households:
- `access`: whether households can use services.
- `prices`: prices households pay, e.g., energy tariffs.
- `data_privacy`: control over personal data.
- `employment`: hiring, monitoring, job outcomes.
- `information`: information environment, content, elections.

### 3.3 Events (facts)

One row per dated event in the text.

- `event` is one of the event types in `vocab.json`. Legislative steps: `introduced`, `consultation`,
  `committee_approved`, `passed_chamber` (say which chamber in `applies_to`), `trilogue_agreement`,
  `legislative_approval` (final passage), `vetoed`, `withdrawn`, `lapsed`. Other types:
  - `application` = a specific obligation, eligibility or regime starts to apply (say which in `applies_to`);
  - `deadline` = a compliance or procedural deadline;
  - `phase_in_step` = a step in a staged schedule.
- `date` is `YYYY`, `YYYY-MM` or `YYYY-MM-DD`, or null.
- For proposals, a bill's history or a legislature's record counts as text evidence when it is part of the
  fetched document. Otherwise legislative steps are `external` events citing the legislature's official page.
- `date_type`:
  - `absolute`: the date is stated;
  - `relative`: "18 months after entry into force"; give the `anchor`, plus `offset_value` (18), `offset_unit`
    (`days`, `business_days`, `weeks`, `months`, `years`) and `anchor_event` (the event type the period counts
    from, e.g. `entry_into_force`, `published`). Fill `date` only if the text states it; the runner computes it
    from the anchor event's date (business days are not computed);
  - `conditional`: "on a date set by decree" or "upon certification"; give `depends_on` or `anchor`;
  - `not_stated`: the event happened but the text gives no date;
  - `external`: from outside the text. Allowed **only for events**, with `external_evidence {url, description}`
    pointing to an official source (e.g., a gazette notice of repeal). Never use memory.
- `date_text` gives the wording as written.
- Session-law history notes ("Added by Acts 2013 … eff. September 1, 2013") count as text evidence.
- Dates shown only in an official database's metadata or dateline (publication date, entry into force on a
  legal portal) are `external` events citing that page.
- **Procedure mapping.** Final vote before signature (e.g., "vom Bundestag beschlossen") =
  `legislative_approval`; a bill sent to the second chamber = `received_chamber`; a bill that died or returned at
  the end of a session = `returned_carried_over`; a constitutional court's prior review =
  `constitutional_review`. China: approval at an agency meeting (审议通过) = `adopted`; the order or notice date =
  `signed`; posting on the official site = `published`.
- Relative dates counted in business days are left with `date: null` (the calendar depends on holidays);
  periods in months or years are computed to the day when the anchor date is known.
- `date_type: recurring` for repeating dates ("every three months", "by 15 January each year"); give the
  rule in `date_text`. Repeated procedural limits that apply to many steps (e.g., 20 working days for any
  authority reply) are one row with the steps listed in `applies_to`, not one row per step.
- **Vintage rules** (duties that depend on when a facility starts operating, or cut-offs tied to
  decommissioning): one `application` or `phase_in_step` event per cohort, with the cohort in `applies_to`
  (e.g., "data centres starting operation from 2026-07-01").

### 3.4 Thresholds (facts)

One row per numeric cutoff that changes legal treatment.

| Field | Content |
|---|---|
| `variable` | Code from `vocab.json`; `variable_text` gives the text's wording |
| `operator`, `value` | Operator and number; `value_max` for ranges |
| `value_text` | Wording as written |
| `unit`, `currency` | Units and currency |
| `indexed` | True if adjusted automatically (e.g., by CPI) |
| `measurement` | Window, aggregation and who measures it |
| `level` | `entity`, `group` (including affiliates), `facility`, `service`, `model`, `product`, `person`, `jurisdiction`, `other` |
| `trigger` | What crossing does: `scope_definition`, `eligibility`, `exclusion`, `obligation`, `exemption`, `benefit`, `benefit_duration`, `designation_category`, `penalty_tier`, `presumption`, `prohibition` (crossing makes the conduct prohibited), `target` (a policy target, not a legal consequence), `cap` (a ceiling such as a price or volume cap), `pricing_tier`, `phase_in` (crossing only changes when duties start) |
| `consequence` | One line saying what happens |
| `conditions` | Other conditions that must hold jointly |

**Rules for thresholds:**
- **What counts.** A threshold is a number at which the law's treatment of someone changes: scope, eligibility,
  exemption, an obligation tier, a prohibition, a benefit, a penalty tier, a price tier. Technical performance
  specifications (voltage tolerances, sampling rates, accuracy classes) count only when crossing them decides scope,
  eligibility or a legal consequence; otherwise they belong in the obligation that requires them. Price
  surcharges or tariffs that apply above a limit (e.g., an electricity surcharge above a PUE value) are
  `pricing_tier` thresholds; penalties for breaking a rule are enforcement. Policy targets of the government are
  obligations, not thresholds.
- Do not code numbers the text attributes to private terms (e.g., a platform's minimum age in its own terms
  of service).
- Do not code procedural time limits as thresholds; they are events (`deadline`).
- Do not code penalty maxima as thresholds; they go in enforcement.
- Thresholds delegated to another act: `value: null`, `value_text: "set by …"`, `depends_on`. Size classes
  defined in another law (SME, micro-enterprise, startup) are coded the same way.
- `currency` may be a unit of account (`UTM`, `UF`, `UMA`) when the text uses one.
- The same cutoff defined separately in two codes or articles is two rows.

### 3.5 Obligations (facts, Tier A)

One row per distinct duty: `type`, `addressee` (a role), a one-line `summary`, `applies_from`, `conditional_on`.

- Duties of government bodies (e.g., "the comptroller shall adopt rules") use `type: government_duty` and
  `addressee: government_agency`. When a public body is bound as a user or deployer of AI (e.g., to assess the
  impact of its own systems), use the specific type (`impact_assessment`, …) with `addressee:
  government_agency`.
- Eligibility conditions for a benefit use `eligibility_condition`.
- **Granularity: one row per article, addressee role and obligation type.** All duties of the same type that one
  article places on the same role are one row (quote the main one, summarise the rest in `summary`); split only
  when start dates differ. Do not split enumerated sub-items. Work through the operative provisions in order, so
  that no article is skipped. (A first rule of one row per paragraph made annotators list over 200 rows for one
  data protection law, mostly noise.) An identical duty on several roles is one row: the main role in `addressee`, the others in
  `also_addressees`.
- `modality`: `shall` (default), `shall_not`, `may` (a permission that matters, e.g., an opt-out), `encouraged`
  ("the State encourages providers to …"). Record encouraged conduct only when it names an addressee.
- Principles worded as statements ("processing takes place in compliance with …", "guarantees") are obligations
  only when an addressee and a conduct are identifiable; otherwise they inform the summary.
- Delegations of legislative or regulatory power to the government (e.g., "the Government is delegated to adopt
  decrees within 12 months") use `type: delegated_power`, `addressee: government_agency`, with the deadline as a
  `deadline` event.
- Quantities that size a government duty (a national savings target in TWh) are obligations of the government,
  not thresholds.
- An obligation with a second character (an impact assessment inside a reporting duty) keeps the main type and
  names the second in `summary`.

### 3.6 Enforcement (facts, Tier A)

One row per sanction regime: `sanction_type`, `authority`, `triggered_by`, and the maximum penalty.
- `max_penalty_text` and amount only if stated in this text.
- If the text only cross-references the penalty (e.g., "GDPR Art. 83(5)(e)"), fill `penalty_reference` and
  leave the amount null; never fill in amounts from memory.
- Also record `private_right_of_action` (true, false, or null when the text neither creates nor excludes one;
  explain in `notes`) and `cure_period`.
- Court-imposed civil penalties recovered by a public authority are `civil_penalty`; fines imposed by an agency
  are `administrative_fine`.
- Revenue-based caps and multipliers go in `penalty_formula` (e.g., "2% of annual revenue; 4% for repeat
  offenders that are not small firms").

### 3.7 Definitions (facts, Tier A)

Terms defined in the text that determine scope: e.g., "AI system", "data center", "qualifying job". The quote
is the definition itself. Skip purely procedural definitions. A scope-determining term defined only by reference
("'AI system' has the meaning given in Article 3(1) of Regulation (EU) 2024/1689") is recorded with
`defined_in` naming the other act.

### 3.8 Relations (facts)

Relations **stated in this text**:
- `legal_basis`: made under powers in another instrument;
- `implements`, `amends`, `repeals`, `transposes`, `preempts`, `codifies`, `replaces` ("repeal and reenact"
  is one `replaces` row);
- `designates_under`: designates authorities or applies powers under another act that it does not implement as
  such (e.g., national market-surveillance powers under Regulation (EU) 2019/1020);
- `enacted_by_bill`: the session law or bill that enacted this text;
- `cross_references`: substantive interaction; say what in `note`.

One row per target instrument: never list several instruments in one row. Give `target_instrument_id` if the
target is in the registry, else null with `target_text`. Relations stated
only in *other* instruments are recorded in those instruments' annotations, or in `registry/links`, not here.

### 3.9 Entities (facts, Tier A)

Named firms, facilities or public bodies with a role: `addressee` (the text is addressed to them), `designated`,
`beneficiary` or `listed`. Public authorities that the text designates or empowers (competent authority, market
surveillance, single point of contact) are `designated`, with their role in `function`; one row per body, with
several functions listed together. Fill `lei` or `ticker` only when verified; otherwise leave them null.

## 4. Tier and annotator metadata

- `tier` comes from triage (`registry/triage.jsonl`).
- `annotator.model` is the model ID or a person; `annotator.method` is e.g. `single-pass`, `multi-pass x3`,
  or `manual + model`.
- `validation`: `machine` → `spot-checked` → `validated` (`playbooks/verify.md`).

## 5. Language

Quotes stay in the original language. Summaries, classifications, `consequence`, `summary` and `note` fields
are in English.

## 6. Edge cases (validator-enforced where possible)

1. An empty required section with no `section_status` fails. Entries plus a `section_status` also fails.
2. `primary_domain` must be in `domains`.
3. `date_type: absolute` requires a date. `relative` and `conditional` require an `anchor` or `depends_on`.
   `external` requires `external_evidence`. Every non-external event needs a text quote.
4. A threshold with `value: null` needs `depends_on`. A `range` needs `value_max`.
5. Individual orders (enforcement measures against one party): the territorial scope includes `targeted`, and
   the addressee appears in `entities`.
6. Preamble and recital text can support the summary and the classification, but obligations and thresholds
   must cite operative provisions.
7. Repealed instruments are annotated as of their last in-force text, with a `repealed` event.
8. When the text is internally inconsistent (e.g., two different values for the same threshold), code both
   rows and explain in `notes`.

## 7. Versioning

The codebook, vocabulary and schema share a version (`schema_version`). Adding values is a minor version;
renaming or removing values or fields is a major version and requires migrating existing annotations.

- **v1.2 (11 Oct 2026),** from the gold-set feedback. New values: roles (`enterprise` for duties on any firm above a size test, `cloud_service_provider`, `data_holder`,
  `ai_distributor`, `hardware_supplier`, `auditor_assessor`, `essential_entity`, `browser_os_provider`,
  `research_institution`, `ethics_committee`); obligation types (`management_system`, `verification_gatekeeping`, `bias_mitigation`,
  `training_data_governance`, `complaint_mechanism`, `minors_protection`, `ethics_review`, `delegated_power`);
  sanctions (`warning_reprimand`, `service_suspension`, `blocking`, `civil_penalty`); threshold variables
  (`volume`, `process_node`, `share_of_financials`, `water_efficiency`, `market_share`, `rd_investment_share`) and
  triggers (`prohibition`, `target`, `cap`, `pricing_tier`, `phase_in`); `recurring` dates; events `received_chamber`,
  `returned_carried_over`, `constitutional_review`; relation `designates_under`. New optional fields:
  `obligations.also_addressees`, `obligations.modality`, `definitions.defined_in`, `entities.function`;
  `private_right_of_action` may be null. v1.1 files stay valid; the gold set was written under v1.1 and has not
  been migrated to the new values.
- **v1.3 (13 Oct 2026),** from the Haiku pilot (`docs/pilot_2026-10.md`): event fields `offset_value`,
  `offset_unit`, `anchor_event` (relative dates computed in code); rules on what counts as a threshold (technical
  specs, surcharges, targets), obligation granularity (one row per article, addressee role and obligation type), and one relation row per
  target instrument.
